# C3 SPI clock 18 MHz → 16 MHz (esp32-balloon-integration-fresh)

**Date:** 2026-09-11
**Task:** `t_ac4a69c8` (C3-SPI-CLOCK)
**Sibling / precedent:** `balloon-fresh` P0.4 `t_0b2f5534` —
`docs/lr2021-p04-spi-clock-16mhz-2026-09-11.md`

---

## 1. What the change is

The dual-MCU integration tree carries three copies of the ESP32-C3 radio HAL. The
`flrc-bench-espidf` copy drove the LR2021 over GPSPI2 at a hard-coded **18 MHz**,
above the LR2021 datasheet maximum of **16 MHz**:

```c
// mesh-stack/flrc-bench-espidf/main/EspHalC3.h
-      dev_cfg.clock_speed_hz = 18000000;
+      dev_cfg.clock_speed_hz = ESPHAL_C3_SPI_HZ;   // 16 MHz (LR2021 datasheet max)
```

with a new single source of truth next to the other HAL constants:

```c
#define ESPHAL_C3_SPI_HZ   (16 * 1000 * 1000)
```

The interactive bench app now self-reports the clock it configures, so a flashed
board states its own SPI speed at boot:

```c
// mesh-stack/flrc-bench-espidf/main/bench_main.cpp (app_main)
printf("  SPI clock = %d Hz\n", ESPHAL_C3_SPI_HZ);
```

### Why 18 MHz mattered

Same defect class as balloon-fresh P0.4: 18 MHz ran fine at ~1 m bench distance
but left zero timing margin against the datasheet, which shows up as SPI timing
failures with real link margin, temperature swing and supply droop — i.e. in
flight rather than on the bench.

### HAL copies in this tree

| Copy | Clock | Status |
|------|-------|--------|
| `mesh-stack/flrc-bench-espidf/main/EspHalC3.h` | 18 MHz → **16 MHz** | fixed here |
| `tracker/firmware/main/EspHalC3.h` | 2 MHz | compliant, untouched |
| `tracker/ground-station/receiver/main/EspHalC3.h` | 2 MHz (symlink to the above) | compliant, untouched |

## 2. Regression gate (TDD RED → GREEN)

New host-only test `tests/test_c3_spi_clock.py` (8 tests, no board required). It
parses **every** HAL copy plus the bench radio apps, so a new/forked copy cannot
silently drift back above spec.

```
# RED — pre-fix revision (18 MHz literal, no macro):
/opt/miniconda/bin/python3.13 -m pytest tests/test_c3_spi_clock.py -v
  -> 5 failed, 3 passed
     test_spi_hz_macro_within_datasheet_max        FAIL  macro not defined
     test_spi_hz_macro_is_arithmetic_and_nonzero   FAIL  macro not defined
     test_radio_device_config_uses_the_macro       FAIL  ['18000000']
     test_no_literal_radio_spi_clock_above_spec    FAIL  EspHalC3.h:130
     test_firmware_reports_the_same_clock_it_configures FAIL bench_main.cpp

# GREEN — after the edit:
/opt/miniconda/bin/python3.13 -m pytest tests/test_c3_spi_clock.py -v
  -> 8 passed
```

The suite also asserts the historical 40 MHz and 18 MHz values *would* be
rejected, so the violation cannot reappear unnoticed. `C3_HAL_PATH=<file>`
reproduces the RED case against any revision:

```bash
git show HEAD:mesh-stack/flrc-bench-espidf/main/EspHalC3.h > /tmp/EspHalC3_18MHz.h
C3_HAL_PATH=/tmp/EspHalC3_18MHz.h /opt/miniconda/bin/python3.13 -m pytest \
    tests/test_c3_spi_clock.py -v
```

## 3. Build + artifact verification (hardware-free)

ESP-IDF v5.4.1, `esp32c3`. Tools are not on `PATH` on this host (`export.sh` is
broken — missing `xtensa-esp-elf-gdb` and a lock-guarded openocd wrapper), so the
environment is assembled by hand. **esp32c3 is RISC-V**: the compiler cmake needs
is `riscv32-esp-elf-gcc`, not the xtensa one:

```bash
export IDF_PATH=~/esp/esp-idf
export IDF_PYTHON_ENV_PATH=~/.espressif/python_env/idf5.4_py3.11_env
export ESP_ROM_ELF_DIR=~/.espressif/tools/esp-rom-elfs/20241011/   # else cmake dies in tools/cmake/gdbinit.cmake:40
export PATH=~/.espressif/tools/riscv32-esp-elf/esp-14.2.0_20241119/riscv32-esp-elf/bin:$PATH
export PATH=~/.espressif/tools/xtensa-esp-elf/esp-14.2.0_20241119/xtensa-esp-elf/bin:$PATH
~/.espressif/python_env/idf5.4_py3.11_env/bin/python ~/esp/esp-idf/tools/idf.py -B <build> build
```

(Without the riscv32 path cmake fails with *"The CMAKE_C_COMPILER: riscv32-esp-elf-gcc
is not a full path and was not found in the PATH"*.)

### Artifact gate

The constant handed to `spi_bus_add_device()` must be 16 000 000 and neither
18 MHz nor 40 MHz may survive in the image. `readelf --debug-dump=info | grep
16000000` **does not work here**: on RISC-V GCC splits the constant into a
`lui`+`addi` pair and this build emits no `DW_AT_GNU_call_site_value` DIE holding
the struct field, so that grep is empty for both the fixed and the broken
revision — it would pass vacuously. The authoritative check is the companion
script, which reconstructs the `lui`/`addi` constants and inspects the
instruction window that feeds the `spi_bus_add_device()` call:

```bash
export PATH=~/.espressif/tools/riscv32-esp-elf/esp-14.2.0_20241119/riscv32-esp-elf/bin:$PATH
python3 tools/verify_c3_spi_clock_elf.py <build>/flrc-bench-espidf.elf \
    --objdump riscv32-esp-elf-objdump
```

Observed on the clean build (exit 0):

```
spi_bus_add_device call sites: 1
constants reconstructed: 121
expected clock in call window: 16000000 -> yes
OK: firmware configures the LR2021 SPI clock at 16000000 Hz (<= 16000000 Hz datasheet max);
    no 18 MHz / 40 MHz constant.
```

Disassembly at the call site — `a5 = 16 000 000` immediately before the call:

```
42007474:  00f427b7   lui   a5,0xf42          # 0xf42 << 12 = 15 998 976
42007478:  40078793   addi  a5,a5,1024       # +1024        = 16 000 000
42007486:  02440613   addi  a2,s0,36         # &dev_cfg
4200748a:  002c       addi  a1,sp,8
4200748c:  5cd070ef   jal   4200f258 <spi_bus_add_device>
```

The raw-byte scan (any little-endian 32-bit occurrence of 18 000 000 or
40 000 000 anywhere in the ELF) also returns zero.
